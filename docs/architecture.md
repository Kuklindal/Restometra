# Архитектура Restometra

Vue-приложение обращается к FastAPI по REST API `/api/v1`. Backend — модульный монолит. API обрабатывает HTTP и валидацию, SQLAlchemy описывает данные, Alembic управляет схемой PostgreSQL. Модули расписания, дневного расчёта и отчётов используют общие модели. APScheduler работает отдельным процессом.

## График и операционная дата

Недельный график задаётся с понедельника по воскресенье в часовом поясе IANA. Исключение заменяет график операционной даты целиком. Время закрытия раньше открытия означает переход на следующие сутки. Явный круглосуточный режим задаёт основной интервал от локальной полуночи до следующей полуночи. Для неоднозначного времени при переводе часов выбирается первое вхождение. Время в пропущенном интервале переносится на первую доступную локальную минуту.

Рабочие интервалы используют полуоткрытые границы `[открытие, закрытие)`. Валидация проверяет пересечения в течение суток, при переходе через полночь, на стыке недели и вокруг исключений. Запас наблюдения добавляется к каждому интервалу и ограничивается началом ближайшего следующего интервала. Момент готовности определяется концом последнего окна наблюдения плюс отдельная технологическая задержка. В пятницу при закрытии в 02:00 субботы, запасе 30 минут и задержке 60 минут обработка возможна с 03:30 субботы.

Операционная дата визита определяется началом визита внутри рабочего окна с учётом запаса. Например, начало в субботу в 01:30 относится к пятничной смене, если она работает до 02:00. Начало ровно на границе двух окон принадлежит следующему окну. События, уже сохранённые и привязанные к визиту, наследуют его операционную дату, в том числе при задержке гостей после окончания наблюдения. Длительность рассчитывается по сохранённым границам визита, даже когда визит закончился на следующие сутки.

Часовой пояс, границы использованных интервалов и обработанные данные сохраняются в дневном снимке. Правка расписания применяется к дальнейшей обработке. Явный пересчёт выбранной даты использует актуальный график. Уже назначенная операционная дата визита фиксируется при первой успешной обработке, чтобы изменение графика не переносило визит в соседний день и не удваивало его в периоде. Если при явном пересчёте дата стала выходной, её новый снимок отражает выходной.

## Обработка и полнота

Фоновый процесс каждые 30 секунд проверяет даты с начала наблюдения ресторана до текущей локальной даты. PostgreSQL блокирует параллельный расчёт по паре «ресторан и дата». После аварийного прерывания соединение освобождает блокировку, следующий процесс может взять незавершённое задание. Повторная обработка атомарно заменяет дневной снимок. Пока пересчёт выполняется, отчёт продолжает показывать предыдущий готовый снимок. Задание со статусом ошибки автоматически повторяется после пяти минут.

Обработка подтверждённо полного дня без визитов даёт нулевые счётчики. Если полнота входных данных не подтверждена, день получает `WAITING_FOR_INPUT` и не входит в итоговые показатели. В деморежиме готовность входных данных указывается при заполнении БД. Для необработанных рабочих дней и дней с неполным входом отчёт указывает пропущенные даты. Выходные отображаются отдельно. Даты и обработчики привязаны к конкретному ресторану.

После дневного расчёта хранятся счётчики, почасовое распределение, измеренные длительности и времена первого контакта для ресторана и отдельных столиков. Из них отчёт считает средние по всем доступным измерениям и точные медианы. Визит без окончания не входит в число завершённых и выборку длительностей. Визит без контакта не добавляет нулевого ожидания. Повторные контакты и подачи учитываются отдельно. В аналитические счётчики входят подтверждённые и ожидающие проверки события внутри визита. Отклонённые события доступны в истории. Демонстрационные нормативы — более 5 минут до первого контакта и более 2 часов на визит.

## Будущий вход событий

**График ресторана → определение нужных видеоинтервалов → ежедневный фоновый анализ → события → дневная статистика → отчёты за произвольный период.**

Календарь предоставляет UTC-границы каждого рабочего окна до конца наблюдения. Будущий обработчик сможет выбирать доступные фрагменты только из этих окон, проверять их полноту, сохранять события и отмечать готовность входа. Для выходного дня окон нет. API отчётов читает дневные снимки. Первая версия получает события из демонстрационной выборки.
